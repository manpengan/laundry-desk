# Windows 全新空库初始化与现场核对材料

本材料可供审阅；当前软件和发行仍是 `development_only`，ADR-98 未签署，**只能用合成身份与数据验收**。
初始化成功不等于获准营业。正式使用须将最终发行组合、技术验证、真实人员和介质证据提交 manpengan 签署，
并按获准发行说明执行，不能自行改清单、状态或入口的 assurance。

## 已决定的范围

- 宏发单店、Windows 10；日常店长一名，负责人兼数据责任人、备份保管人与独立复核管理员。
- 空库开始，不读取、不导入 v1。新实例必须是新根，不能清空、转换或改名复用 QA 实例。
- 试点日期在最终发行实机验收后确定。每天 03:00 自动备份，电脑夜间开机并保持指定 Windows 用户登录。
- 两个管理员在现场分别自选长密码与 PIN，不在聊天、仓库或交付包传递个人凭据。
- 本轮打印暂缓，不计为通过。Cloud 相关入口继续隐藏；短信、支付、AI 的真实账号与具体测试授权由负责人后续准备。

以上操作选择不构成 ADR-98 全文签署。RPO/RTO、容量、留存/响应阈值、分发签名政策和豁免仍须形成可追溯裁决；
软件初值或旧草案建议值不能被当作承诺。人员姓名和联系方式在仓库外保存。

## 合成演练与后续正式初始化的步骤

1. 固定同一源码的 Counter 和 Runtime。用可信外部记录核对 ZIP、安装器、EXE、Runtime manifest、
   生成入口及 operator 文件的 SHA-256；保存不含秘密的来源记录。CI 与手册齐全不替代新候选实机验收。
2. 选择明确的 Windows 用户与全新实例。检查
   `%LOCALAPPDATA%\laundry-desk-v2\runtime-companion` 不存在，并确认 8787/8543 没有其他服务。
   若存在实例、旧数据或未知任务，停止本次新装，保留它们；不得删目录、停未知服务、借换用户名绕过现有任务或修改状态。
   合成演练应在独立受控机器/用户环境完成，不能再把这一演练实例认作正式空库。
3. 双击已核对的 `Laundry Runtime V2.cmd`，选择 **“初始化全新空库”**。
   **“安装本地服务”仍是原合成自动安装**，会生成测试凭据，不能代替现场自选身份。
4. 两位操作者分别填写登录用户名（ASCII 字母/数字/`_ . -`，1–64 位）、显示姓名（1–80 位）、
   密码（12–256 位）与 PIN（6–8 位数字）。密码和 PIN 各输入两次，且两人的账号、密码、PIN 各自不同。
   核对确认框后开始；取消不会创建实例。当前验收全部使用明确标识的合成身份。
5. 等待明确成功结果：状态 running、`initialization=operator_new_empty`、`admission=pending`、
   `assurance=development_only`，以及正确的 source/manifest/migration 绑定。
   入口实际执行 `roles → migrate → bootstrap → verify-commissioned`，清除个人输入后才启服务。
   只看到窗口、绿色健康、已有 CLI 或安装器退出均不足以确认本步骤完成。
6. 检查 `bootstrap-input` 已不存在，`secrets` 不存在此次生成的 `laundry-bootstrap-admin-*` / `laundry-bootstrap-approver-*` 文件；
   **只记录是否存在，不打开或复制秘密内容**。数据库连接/令牌运行密钥应继续存在并受保护，不删除它们。
7. 用成套 Counter 分别验证两身份登录与独立复核；普通店员越权应拒绝。合成验收另做重启、注销/登录、
   备份验证/恢复、既有实例拒绝和中断场景，核对重启后不再读取个人初始化输入。保存动作、时间、摘要和固定错误码，
   不保存密码/PIN、输入窗口截图、客户正文或数据库内容到公开报告。
8. 日常店长在独立合成演练实例完成开单、取衣、交班和备份，负责人核对结果。真实业务新根保持空库，
   初始核对只验证账号、权限、配置、备份与新库身份，不用“做几笔测试再清空”准备正式库。
9. 在签署前明确计划任务实际时刻、机器开机/登录条件、独立介质与口令保管、恢复目标、故障接替与停写条件。
   真实短信/支付/AI 单独按具体授权测试并留脱敏回执；打印继续暂缓。未获准项保持关闭。
10. 将最终组合与剩余事项交 manpengan 审阅；明确批准的真实范围生效后，才按该范围开始业务。
    实施者不得代签，也不以技术初始化结果自动开放真实数据。

## 失败与受控脚本入口

`STORE_REQUIRES_NEW_INSTANCE` 表示根已存在；不重试覆盖。验证失败只留 staged 恢复记录，个人输入正常情况下已清除，
不注册启动任务。若错误为 `STORE_INPUT_CLEANUP_FAILED`，保持失败并保留现场，由维护人员根据固定错误码核对
私有目录/链接异常；不要把它解释为成功或继续手动启动。已登记实例的下次生命周期访问会先尝试清理残留。
`stop` 仍可按既有进程身份受控停机，但清理失败继续返回失败并保留恢复记录。`diagnostics` 仍可导出脱敏诊断，
以固定字段 `setup_input_cleanup=failed` 标明清理问题；不读取或导出残留个人输入，导出成功不代表恢复完成。
半初始化没有自动清空重来功能。

新空库只能使用支持本初始化协议的 Runtime 维护，旧维护程序会被拒绝。升级、回退及保留数据重装必须选用
支持同一协议的发行；出现 `STATE_INVALID` 或 `STORE_RUNTIME_VERSION_REQUIRED` 时，使用已核对的配套新入口处理，
不要修改状态版本、补造个人凭据或清空实例。原合成测试实例仍保留原有版本兼容路径。

自动化入口是已绑定的 `runtime-entry.ps1 -Action install-store`，内部调用同一
`payload\scripts\lifecycle-launch.ps1 -Action install-store`。两者只从继承的有界 UTF-8 stdin 接收一次性 JSON：
外层字段 version=1、mode=new_empty、admin、approver；两人的字段仅 username、displayName、password、pin。
确认副本不传入。普通使用推荐 GUI；测试程序应直接写子进程 stdin 并关闭，禁止把 JSON、秘密、文件内容或连接串拼进
PowerShell 命令、`-EncodedCommand`、命令历史、环境明文或报告，也不绕过受信入口直接调用 Node/bootstrap CLI。
临时私有文件由生命周期内部创建和清理，不需要现场人员手工保管输入文件。
