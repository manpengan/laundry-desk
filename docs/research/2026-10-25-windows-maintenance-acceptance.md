# Windows 维护健康检查与安装验收 — 2026-10-25

本记录接续 PR #259 的安装态维护诊断，不以构建成功或部分回执作为整体验收完成。

## 证据与修复

- main `61b485707b22ece918e8fca011a59f6c6e44458a` 的 Windows Runtime CI `40156516980` 完成 26 场景；其中成功的 `backup-health` 原生调用耗时 **36,391 ms**。
- 同源码宏发 Counter 安装任务 `121081813479` 在维护检查运行 36.0 秒后报 `COUNTER_BACKUP_HEALTH_ALERT`，面板提示未能连接已绑定的维护程序。旧 Counter 对所有维护调用设置 30 秒截止，短于上述已测成功调用。CI 没有保存内部失败分支，不能仅凭面板文案断言它一定命中计时器；预算不兼容本身已由成功耗时证明。
- 健康检查单独使用 90 秒有限预算，打开窗口和交接保持 30 秒。响应处理独立回归覆盖超过旧期限的成功、到期拒绝、到期后晚到响应、短窗口期限、会话改变、错误输出、无效 JSON、过量输出和非零退出。完整 Runtime 校验与授权规则不放宽。
- DESKTOP-MAN 的 61b 候选已成功读取备份健康、打开维护窗口，并在 Counter 退出后存活；原测试在窗口初始化忙时只发一次关闭请求，随后等待退出失败。产品 `FormClosing` 会拒绝忙时关闭，不会重放该请求。
- 同一窗口完成后，核验 PID、创建时间、用户、会话、可执行路径、标题及 23 个按钮恢复可用，正常关闭在 **186 ms** 内退出。初次失败时未采集即时忙标志，故这一机制与后续实测支持时序问题解释，仍需新原生回归及安装版复验确认。
- 安装态测试改为检查原生健康完成文案与按钮父链可用，再按同一身份正常关闭；不强杀。回归用原生 WinForms 忙窗口及确定性握手验证关闭时序与错误身份拒绝。原始失败和收尾失败一并保留，成功回执在完整收尾后写入。
- 第三轮 61b 目标机诊断中，generic 完整维护检查与正常关闭通过；hongfa 等待健康结果时面板消失，后续读取面板文字再次超时，覆盖了原始等待错误。不能把这一轮归因为关闭失败，也不能仅凭旧预算推断实际根因。后续诊断须在有限时间内采集非敏感页面状态，并始终保留主错误。
- `debb892a989fd5d48d264eded1fc6e077eca4101` 的完整 CI 检出新增 `windows-response.js` 未进入两份 Electron 打包白名单，虽然安装器结构构建已完成，该候选仍不具备交付资格。此问题由依赖闭包回归直接定位；Mac 安装包启动同时超时，但没有独立内部错误证据，不能把超时单独视为根因证明。修复白名单后，闭包检查前移至统一 `beforePack`，缺失构建文件或传递依赖时立即终止打包。
