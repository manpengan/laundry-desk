# ADR-91：PR #229 统一修复与第 2 批范围裁决

- 日期：2026-10-04
- 状态：Accepted。2026-10-04，manpengan 在会话中授权：本次修复由 Claude 统一实现、测试并合入 main，Codex 不并行；D-1～D-4 也由 manpengan 选定。
- 关联：ADR-66、ADR-71、ADR-16、ADR-77、ADR-79、ADR-82、ADR-83、ADR-85
- 证据：Claude 2026-10-04 的审核与 winbox 实测（知识库 `projects/laundry-desk/evidence/2026-10-04-pr229-winbox`）、本 ADR“验证”一节

## 背景

PR #229（Codex Windows 全功能批次）CI 全绿，但审核与 Windows 实测发现以下问题：

- 扫码收款结果不明时，订单被锁死。现金取衣返回 500 和英文错误。
- 浏览器/局域网模式下有 9 个 HTTP 端口以方法形式调用 `window.fetch`，报 Illegal invocation。
- 短信模板参数按“分”发送。短信失败一律记为“结果不明”，且不写日志。
- AI 出现任意异常后停用整个组织的 AI。
- 笔记本用电池供电时，Runtime 不自启。
- 新设置面板没有样式；金额按“分”或“微单位”填写。
- 两个发行版共用 Electron 用户数据目录。

ADR-71 暂停 Cloud 后，需要公网 HTTPS 入口的功能处于不可用状态，需要裁决。

## 决策

### 1. 外部调用结果统一三分类

支付、AI、短信共用以下判定：

| 类别                | 判定                                                               | 处理                                 |
| ------------------- | ------------------------------------------------------------------ | ------------------------------------ |
| 未发出（not_sent）  | 域名解析、连接被拒或不可达、TLS 证书被拒；本地凭据、签名、参数失败 | 不计费，释放预留与订单锁             |
| 被拒绝（rejected）  | 对方给出可验证的明确拒绝：HTTP 4xx 或业务错误码                    | 终态，释放预留，显示可操作的中文原因 |
| 结果不明（unknown） | 请求可能已被受理：发出后中断、5xx、2xx 应答无法解析或验签          | 走查询或人工处理，保留预留           |

“未发出”只依据错误原因链里能证明连接从未建立的错误码判定，统一由 `apps/server/src/http/unsent-failure.ts` 实现。每次没有成功受理，都写一条结构化日志，不含手机号、正文和密钥。

### 2. 扫码收款（修订 ADR-85）

- **派发**：未发出或被拒绝时立即判为 closed，错误码为 `CHANNEL_NOT_SENT`，或 `CHANNEL_REJECTED_<渠道码>`（渠道码经过净化）。其余失败为结果不明。
- **过期关单**：`expires_at` 加 2 分钟宽限后，worker 主动关单。
  - 微信：调用 close，再查询。
  - 支付宝：调用 `alipay.trade.cancel`；返回 `retry_flag=Y` 时保持结果不明。
  - 渠道答复订单不存在或已关闭、且没有任何收款时，判为 closed，错误码 `CHANNEL_EXPIRED`。
- **自动查询**：
  - 过期前每 10 秒一次，过期后 30 分钟内每分钟一次，之后每 10 分钟一次。
  - 过期满 24 小时仍无结果，转为 `needs_review`（`CHANNEL_REVIEW_REQUIRED`）。没有渠道单号的 needs_review 不再自动查询。
- **人工核销** `resolve`：
  - 条件：管理员权限、当前管理员密码、4–200 字的核对依据；意向处于 unknown 或 needs_review；没有渠道单号和收款记录；已过宽限期。
  - 结果：判为 closed（`CHANNEL_MANUAL_CLOSED`），同时写审计 `payment.channel.close_unconfirmed`。
  - 不提供“判为已收款”的手工入口，只有渠道核实的收款才入账。渠道后台显示已付的，仍由查询自动结算；对账导入也会报告缺失。
- **收款入口回到业务流程**：
  - 取衣页的扫码卡片由有 `order_write` 权限的店员使用，可调用 `available`、`checkout`、`status`、`list`（必须带 order_id）和 `close`。
  - 开单成功后，结果区出现同一张卡片，顾客可当场扫码预付；渠道确认的金额会更新结果区的已付与欠款。开单提交本身不改：订单要先存在，才能按欠款出码。
  - 设置页只保留收款记录、原路退款、账单核对、商户设置和人工核销，这些仍只限管理员。
- **订单锁的错误**：
  - 数据库守卫 `CHANNEL_PAYMENT_PENDING` / `CHANNEL_REFUND_PENDING` 映射为 `RESOURCE_UNAVAILABLE` 加 `reason: payment_pending`。
  - `CHANNEL_REFUND_REQUIRED` 映射为 `POLICY_DENIED` 加 `channel_refund_required`。
  - HTTP 状态沿用命令总线的约定：业务错误为 400，授权为 403，事务失败为 500。不引入单独的 409，由 code 和 reason 区分。
- **协议加固**：
  - 微信 `time_expire` 改为带 `+08:00` 的 RFC3339（精确到秒）；官方标为选填的字段做容错。
  - 签名与未签名应答分开判定。
  - 支付宝全额退款后的 `TRADE_CLOSED` 对已 paid 的意向幂等。
  - 退款被渠道告知“不存在”时，用同一退款号重新提交。
  - 解密移到行锁事务之外，适配器按配置版本缓存 2 分钟。
- **对账**：直接导入以下官方账单，规范五列 CSV 保留为“高级”选项。只核对本系统发起的流水，跳过的行会计数显示。
  - 微信“交易账单（全部）”：列名按官方文档核对过。
  - 支付宝“业务明细”：GBK 编码；列名依据公开资料，首次用真实账单导入时须核对。
- **契约面**（ADR-16）：
  - 桌面/HTTP 新增 `available`（GET）和 `resolve`（POST）两个操作，新增 `ChannelAvailabilityViewSchema` 和 `ChannelResolveInputSchema`。
  - `ErrorDetail.reason` 增加 `payment_pending` 和 `channel_refund_required`。
  - 这些不是总线命令，`m2-freeze` 清单不变；OpenAPI 快照已重新生成。

### 3. AI 用量与隔离（修订 ADR-82；ADR-83 视觉走同一运行器）

- 失败带上内部的“未计费”标记，不改变对外错误码。以下情况不扣费、不隔离，只计入熔断：
  - 供应商在任何输出前返回 HTTP 错误；
  - 请求没有离开本机；
  - 凭据格式本地校验失败。
- 已开始输出后中断，或没收到用量：按预留全额扣费，记为 `usage_unknown`。店员主动停止也扣预留，但不计入隔离。
- 只有两种情况停用 AI 配置：
  - `outside_contract`；
  - 同一门店在滚动 24 小时内第 3 次 `usage_unknown`。计数从“24 小时前”与“策略最近一次保存”中较晚的时刻开始。
- 迁移 0080 替换 `ai_usage_quarantine`。未达阈值时审计为 `ai.usage.unknown`，停用时为 `ai.usage.quarantine`。
- 恢复方式：管理员核对账单后，在设置页勾选启用并保存。保存即视为已核对，写入审计。
- 预算和单价按元录入，前端按字符串精确换算为微单位。

### 4. 短信（修订 ADR-77）

- **模板参数**：发送 `{tickets, garment_count, balance_yuan}`，金额如 `"20.00"`。不再发送 `balance_cents`，理由：
  - PR #229 从未发布，不存在按它审批的模板；
  - 阿里云没有说明多余变量会如何处理。
- **本地话术**：两种占位都接受，默认改为“尚欠{{balance_yuan}}元”。
- **失败分类**：
  - 本地入参无效：被拒绝（`ALIYUN_INPUT_INVALID`）。
  - 凭据不可用、连接未建立、`isp.SYSTEM_ERROR`：未发出。
  - HTTP 4xx 或业务码：被拒绝，常见码映射为中文原因。
  - 5xx、发出后中断、2xx 应答无法解析：结果不明。
- **预留与重发**：未发出和被拒绝都是终态，释放费用预留，标为“转人工联系”并显示原因。按至多一次的发送约定，不自动重发，由店员带回人工名单。结果不明保留预留。
- **设置页**：费用按元填写；明确写出模板变量。

### 5. 浏览器端口

`createBrowserPorts` 默认用 `(input, init) => fetch(input, init)`，各端口以函数形式调用 `fetchImpl`。另有测试扫描编译产物，禁止 `x.fetchImpl(` 这种方法调用写法。

### 6. Windows 运行时与打包

- **电池**：Companion 和开发 Runtime 任务都设置 `AllowStartIfOnBatteries` 与 `DontStopIfGoingOnBatteries`。注册或启用时检测并修正已有任务。
- **D-4 自动备份**：
  - 安装、修复、升级时，若店主从未保存过备份计划，自动开启每天 03:00 备份。注册失败不留占位文件，下次会再试。
  - 近 7 天没有“加密离机备份”时持续提醒，引导存到 U 盘或 NAS。
- **P1-7 打包身份**：
  - 每个发行版打包各自的 ASCII 包名（`laundry-desk-v2`、`laundry-desk-v2-hongfa`），userData、单实例锁和每用户安装目录因此分开。
  - 通用版首次启动时，通过同卷重命名接管旧的共享目录 `%APPDATA%\@laundry\edge-agent`，保留 ACL 和设备身份。宏发版重新开始，需要重新配对。
- 维护窗口不再显示“远程协助配置”按钮，CLI 动作保留，供技术人员使用。

### 7. 界面

- **D-1/D-2**：设置页隐藏“顾客微信小程序”“微信订阅提醒”“远程协助”。代码保留，可通过 `SettingsPage.publicEntryFeatures` 打开，但任何宿主都不设置它。
- **新面板**：统一使用设计系统，金额一律按元录入；打开时不显示失败文案。命令错误在客户端转为中文；渠道和短信错误码映射为可操作的说明。维护工具中的按钮名与面板说明保持一致。
- **工作台**：“今日实收”和“营业额”与账目页使用同一套计算代码（`stats.day.summary` 新增两个可选字段）。这两项属于账目数据，只返回给有 `accounting_read` 的账号（店长）；其他店员仍看到原来的“收款（退款前）”，查询也不会读取账目。
- **提示**：
  - 页面切换时清除旧提示，宽限 500 ms，保留触发切换的动作所产生的提示。错误提示停留 6 秒。
  - 位置保持顶部居中。Windows 截图证明，任何底部位置都会盖住主操作（开单页的结算栏、取衣页的收款栏）。

### 8. 验收框架

- 已安装形态的验收用例在失败时保存 Electron 主进程日志。evaluate 遇到“执行上下文被销毁”时：
  - 主进程仍存活，等首个窗口后重试一次；
  - 主进程已退出，才判定失败。
- 新功能面板纳入安装态截图，并断言打开时没有告警。
- winbox 上 29 个遗留的一次性 QA 计划任务已导出 XML 备份后删除；代理、开发 Runtime 与 Companion 任务保留。

## 范围裁决（第 2 批）

| 编号         | 裁决                                                                                                                                                        |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-1 公网入口 | 隐藏入口。小程序、订阅消息、支付回调、远程协助支持端、自动更新源需要备案域名的 HTTPS 入口，这与 ADR-71 冲突，待另立 ADR。支付回调未部署不影响主动查询收款。 |
| D-2 远程协助 | 暂缓，随 D-1 隐藏。                                                                                                                                         |
| D-3 电子秤   | 保持现状。                                                                                                                                                  |
| D-4 自动备份 | 默认开启，并提醒存一份异机备份。                                                                                                                            |

## 否决的备选

- **为在途收款单独用 409**：与总线约定不一致，由 code 和 reason 区分即可。
- **人工核销可判为已收款**：会产生无法核实的入账。
- **自动重发未发出的短信**：现有至多一次的领取模型会把第二次领取判为结果不明。要支持，须先在领取时证明此前每次都确实没发出，本批不做。
- **同时发送 `balance_yuan` 与 `balance_cents`**：阿里云对模板未使用的变量如何处理没有文档。
- **提示放在底部**：Windows 截图证明会遮挡主操作。
- **按方案 §6 把 PR #229 拆成 6 个 PR**：manpengan 要求统一实施，改为一个修复 PR，按领域分提交。

## 验证

- **本机**：
  - 单元测试：Web 577 项、契约 855 项、domain 192 项、db 144 项、ui 39 项、edge-agent 147+457 项、tools 479 项全过。
  - 格式、lint、typecheck、Web 构建预算、SPA 同步均通过。
- **真实 PostgreSQL**（隔离的 Docker 栈，迁移 80 个，含 0080）：server 1292 项通过，1 项跳过（Windows DPAPI）。另有 3 项旧版导入草稿测试因本机 better-sqlite3 是 Electron ABI 而无法加载，属环境问题，CI 会按 Node 重编。
- **winbox**（Windows 10）：使用已安装 payload 的副本加本次构建，私有 QA 数据库，网络替身。
  - 浏览器模式无任何绕行：5 个面板打开无告警，3 个入口已隐藏。
  - 扫码收款：
    - 未发出：订单不锁，现金取衣成功。
    - 连接中断：订单被保护，取衣返回中文说明（400，不再是 500）；恢复后店员在取衣页关闭收款，现金取衣成功。
    - 正常：显示收款码，关闭后可收现金。
    - 上午遗留的卡单意向已由 worker 自动关单（`CHANNEL_EXPIRED`）。
  - 短信：`TemplateParam` 为 `balance_yuan:"20.00"`。AccessKey 无效时界面显示“AccessKey 无效…”，预留归零，日志为结构化记录。
  - 0080 由 Windows 安装包里的迁移工具应用。电池策略已在临时任务上验证。
- **未验证**：
  - 真实商户、阿里云和 AI 供应商（本批只用替身）。
  - P1-7 的安装包重命名与宏发安装形态。
  - 10-03 i1 的宏发功能用例复跑（验收框架已加固，下次 Windows 安装验收时复跑）。
  - 拔电源后重新登录的实测。

## 后果

PR #229 的功能连同这些修复合入 main。“未验证”所列各项须在宏发试点前补齐实测证据。人工核销的使用情况和 AI 隔离阈值，试点后复核。
