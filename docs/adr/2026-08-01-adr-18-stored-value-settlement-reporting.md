# ADR-18：储值核销在交班与对账中单列，不进钱箱

- 日期：2026-08-01
- 状态：**Accepted**
- 决策者：manpengan
- 前序：[ADR-17：会员储值](2026-07-31-adr-17-member-stored-value.md)
- 影响：`reconciliation.day.get` 结果面、`payments.method` 类型链、交班口径

## 背景

ADR-17 §6 裁定余额结账写入 `payments`（`method = 'balance'`），理由是它在账面上就是一笔
针对订单的支付，不进 `payments` 会让订单的 `paid_cents` 与日结对账漏掉它。

实现 ADR-17 第二片时，把 `PaymentAppendInput.method` 放宽以容纳 `balance`，类型检查
立刻把这个放宽推到了 `reconciliation`、`shift-close` 与 `stats` 三处。这不是机械修
类型：它逼出一条 ADR-17 只写了半句、没有定义清楚的口径——

> 「统计与对账把余额支付计入订单收款，但它**不是当日现金流入**——充值时才是。」

「不是现金流入」说清楚了钱箱，没说清楚**营业额怎么算、店主在交班面板上看到什么**。
这条不定，PG 存储与 handler 就没法写：写进去的每一笔余额支付都会流向一个未定义的报表。

## 决策

### 1. 钱箱只认现金，且这一条已经成立

`expected_cash_cents = 上日留底 + 当日现金净额`，其中现金净额的两处实现
（`stats/pg-source.ts` 与 `stats/memory-source.ts`）都带 `method = 'cash'` 过滤。

因此**余额支付不会污染抽屉，无需任何改动**。本条是把既有行为固化为裁决，防止后续
有人"顺手"把 `expected_cash` 改成按全部支付方式求和。

### 2. 对账中储值核销单列一行，与现金流入并列

`reconciliation.day.get` 的 `ledger.buckets` 已经是按 `(method, kind)` 分桶的数组。
把 `balance` 加入 `ReconciliationPaymentMethodSchema` 后，储值核销自然成为独立一行，
不与任何现金类方式合并。

这正是店主每天要分开知道的两个数：**今天收了多少钱**，和**今天核销了多少储值**。
合并会同时毁掉两者——现金对不上，储值消耗也看不见。

桶数量上限由 20 提到 **25**：方法 5 × 种类 5 = 25，原上限恰好卡在 4 × 5 = 20，
新增方法后必须同步抬高，否则合法的一天会被 schema 拒绝。

### 3. 营业额包含储值核销，现金流入不包含

- **营业额（订单已收）**：包含余额结账。顾客确实消费了这笔服务，订单确实结清了。
- **现金流入**：不包含。钱在**充值当天**就已进店，计入充值那天的现金。

这是收入确认与现金流确认分离的常规做法。代价是「当日营业额」与「当日现金」在有储值
消费时天然不等——这不是错误，而是储值业务的本来面目，报表必须让它可见而不是抹平。

### 4. 命令级支付方式仍不含 `balance`

ADR-17 §6 的两集合拆分继续有效且不因本 ADR 松动：`PAYMENT_METHODS`（命令入参）
不含 `balance`，`PAYMENT_LEDGER_METHODS`（表可容纳）含。余额的唯一写入路径仍是
`member.balance.pay` 的同事务双写。

放宽只发生在**账本与报表**的类型链上：`PaymentRow`、`BuildPayPaymentInput`、
`PaymentAppendInput`、对账方法枚举。命令边界一个字不动。

## 后果

- `ReconciliationPaymentMethodSchema` 增 `balance`，桶上限 20 → 25，OpenAPI 快照随之更新。
- 契约面**不增加命令或查询**，仅放宽既有结果 schema 的枚举，故不触发 ADR-16 §2 的
  新增门禁；但本 ADR 仍记录该变更，因为它改变了对外结果形状。
- 交班面板与对账导出会出现 `balance` 方法行；读取方法字段的前端需能渲染该值。
- `expected_cash_cents` 的计算逻辑**不变**，并新增回归钉住「余额支付不进钱箱」。

## 否决的备选

- **余额支付不计入当日收款**：抽屉能平，但当日营业额显低，店主看不出储值被消费了多少，
  等于把一块业务藏起来，否决。
- **计入营业额也计入钱箱**：抽屉必然对不平，且差额随储值消费波动，会让真正的现金短溢
  被噪声淹没——这恰好毁掉钱箱核对的唯一用途，否决。
- **把储值核销并进 `other` 方法桶**：`other` 是真实收款方式的兜底，混入非现金流入会让
  两者都失去意义，否决。
- **另建一张储值报表**：店主要在两个地方对同一天的账，且订单侧与储值侧的口径会各自漂移，
  否决。
