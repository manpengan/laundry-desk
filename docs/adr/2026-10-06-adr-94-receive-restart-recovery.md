# ADR-94：Windows 柜台开单的跨重启恢复

- 日期：2026-10-06
- 状态：实现，待最终候选安装态验收
- 范围：D04；继承 ADR-92 的原操作重试身份，未新增 Command/Query，不改变离线授权或真实数据准入。

## 问题

原来的未暂存工作区及主进程重试键仅存在于内存。关闭应用或主进程崩溃后，
原开单是否已落库可能无法确认。只保存 renderer 的 operationId 不足以恢复真正的
HTTP 幂等键；服务端成功但响应或 IPC 回执丢失时不能用新键重开或加入新离线队列。

## 决定

1. 在 Windows Electron 主进程增加独立的 `receive-recovery` 存储根目录。
   按当前受信会话的 org/store/staff/device 分区，路径使用摘要；renderer 不提供租户或路径。
   session ID/version 只作为每次 IPC 调用的前置条件，不作为持久化身份。
2. 复用 OfflineReadCacheFile 的 AES-256-GCM、OS safeStorage 密钥保护、私有目录/文件 ACL、
   symlink/硬链接与文件身份检查、临时文件、fsync/write-through 原子替换机制。
   独立根目录不随退出登录清理 read cache。不得写顾客信息到 localStorage/sessionStorage。
3. 新增固定 `desktop:receive-recovery:operation` IPC，仅提供 load/save/submit。
   输入、输出为严格且有界的 schema；只允许有效 staff/admin 会话，沿用固定主 frame sender 校验。
   每个调用携带捕获的 session ID/version，旧员工的异步保存不能借当前登录写给新员工。
4. 草稿只保存可编辑字段与 operationId，不保存凭据、有效电子秤读数、renderer 声称的收款回执。
   草稿写入失败、损坏、OS 解密失败或身份不符时持续提示并阻断提交，支持原地重试。
5. 提交前先等待草稿安全保存，再将实际 HTTP body 与主进程生成的 Idempotency-Key 原子落盘。
   持久化失败时 HTTP 请求次数为零。相同 operationId 换 body 一律拒绝。
6. 确定回执必须落盘后才返回 IPC；回执落盘失败仍保留 prepared 操作并使用原键重放。
   每次发出尝试前持久化次数；已有未知尝试后的鉴权/校验拒绝不能证明原请求未落库，仍保留待确认状态。
   已完成记录不会删除或复用键，下一单采用新 operationId。未知操作不作 TTL 清理。
   每个操作独立文件，避免一个累计 JSON 的大小限制截断旧身份。
7. 应用重启后仅恢复当前员工的草稿/待确认操作。原完成回执展示前再查询 order.get，
   核对其后扫码付款产生的最新 paid/balance；不能读取最新账目时先阻断展示可支付余额。
   恢复不自动收款、不自动重放；店员明确点击原操作重试。旧小票不会被当作最新扫码收款凭证。
8. HTTP 浏览器没有受保护本机端口，继续使用明确的服务端“暂存挂单”，不承诺自动恢复未暂存内容。

## 安全与维护边界

- 原幂等写入继续通过现有鉴权、权限、不变量和事务执行链；本地回执不能生成新业务事实。
- 主进程收到迟到响应时仍写回原调用员工的记录，不跟随已切换的当前员工。
- unknown 不会转成新离线键；只读恢复/离线只读模式不能执行恢复写入或提交。
- 恢复文件含顾客信息，只归本机 OS 用户；它不替代业务数据库备份，不随诊断导出发送。
  另一个 Windows 用户无法解密时需保留原文件并联系管理员，不自动删除或重置。
- 完成记录保留以防迟到重试；安全归档/清理策略必须另行设计，不能清除仍未知的操作。
- 真实顾客数据仍受 ADR-71 的本机生产准入约束。

## 回归与验收

自动化覆盖：准备写入失败零请求；服务端已成功但丢响应后重建进程仍用原键/body；
同员工新 session 恢复；成功回执已落盘但 IPC 未交付；回执写入失败后原键重试；
员工/组织/门店/设备隔离；过期或不支持角色/旧 session 拒绝；同 ID 换 body 拒绝；
迟到响应归原员工；损坏/加密故障阻断；Web 草稿恢复与未知结果锁定；最新支付金额核对。

最终候选仍须在 Windows 安装态执行主进程强杀、重新登录、原单重试和后端订单/支付行数核对，
并验证磁盘失败提示、150% DPI、中文输入及员工切换。单元测试不替代该实机证据。
