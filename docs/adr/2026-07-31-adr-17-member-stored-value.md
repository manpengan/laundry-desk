# ADR-17：会员储值首期——组织级账户与只追加账本

- 日期：2026-07-31
- 状态：**Accepted**
- 决策者：manpengan
- 路线：[ADR-14：通用 V2 本地优先交付](2026-07-25-adr-14-generic-local-first-v2-delivery.md)
- 门禁依据：[ADR-16 §2](2026-07-31-adr-16-edge-operations-scope-ratification.md)（新增契约面须附 ADR）
- 影响：`packages/contracts` v0.2 冻结面、`customers` 关联、`payments` 支付方式

## 背景

2026-07-19 的产品化转向把**会员储值定为 P0**。但截至 `fcc601c`，29 条命令面里没有
任何会员相关命令：阶段二交付的是履约、员工权限、离线、对账——全是门店内部运营，
**没有一条是面向顾客的留存能力**。本 ADR 开启这条线。

首期只解决一个问题：**顾客可以预存钱，并用预存的钱结账**。储值若不能消费就没有意义，
因此"开户、充值、余额支付、查询"四件事必须一次做完，缺一不可。

## 决策

### 1. 会员账户挂在 `customers` 上，不新建会员实体

`member_accounts` 与 `customers` 一对一，不引入独立的"会员"主体。

理由：`customers` 已经承载手机号唯一、重复合并（`customer.merge`）、隐私脱敏
（`customer.anonymize`）与导出。另起一套会员主体意味着这些逻辑要写第二遍，且两边
一旦不同步就会出现"合并了顾客但余额还挂在旧档案上"这类丢钱问题。

### 2. 账户是**组织级**，账本行记门店

`customers` 是组织级的——迁移 0011 没有 `store_id`，唯一键是 `(org_id, phone)`，
RLS 只按 `org_id` 收敛。会员账户必须与之一致：

- `member_accounts`：组织级，RLS 只比对 `app.org_id`，照抄 `customers_org_scope`；
- `member_ledger`：同为组织级 RLS，但**每一行记录 `store_id`**，用于归属是哪家门店
  收的钱、哪家门店消费的。

账本 RLS 不能按门店收敛：余额是账本的求和，若读取被限制在本门店，A 店充的钱在 B 店
会"消失"，余额直接算错。组织仍是租户边界，本决策不扩大跨租户可见范围。

### 3. 余额是账本投影，不是可更新字段

`member_accounts` **没有余额列**。余额 = `SUM(member_ledger.delta)`。

`member_ledger` 与 `payments` 同姿态：对 `laundry_app` **只授 `SELECT, INSERT`**，
无 `UPDATE` / `DELETE`（反篡改靠权限而非应用自觉）。更正靠 reversal 行。

一个可 UPDATE 的余额字段意味着任何一次写漏、并发覆盖或误改都会让钱凭空增减，且**事后
无法自证**。投影式余额的代价是每次要求和，收益是账实永远一致且可逐笔追溯。

### 4. 账本用带符号增量，不用"正数 + kind"

`payments` 用「正数金额 + kind」。会员账本**不沿用**这个形态，改用带符号的
`principal_delta_cents` / `bonus_delta_cents`。

理由：余额必须是一个朴素的 `SUM`，才能用一条约束校验、用一条查询自证。若用正数加
kind，求和要写成 `CASE WHEN kind IN (...) THEN + ELSE -`，每新增一种 kind 都要回来
改这个 CASE，漏改就是算错钱。带符号后 reversal 恰好是被冲正行的取反，语义闭合。

约束保证符号与 kind 一致：充值为正、消费为负，reversal 不限。

### 5. 本金与赠款从第一天就分列

即便首期充值赠送恒为 0，`principal_delta_cents` 与 `bonus_delta_cents` 也分两列。

理由：多地对预付卡的要求是**本金可退、赠款不可退**。这条一旦到来，若账本只有一个
合计列，就需要回溯拆分历史流水——而历史流水是只追加的，拆不动。分列的成本是现在多一
个恒为 0 的列，不分列的成本是将来无法合规。

消费扣减顺序固定为**先扣赠款、后扣本金**，并在 `member_ledger` 分别记两个增量。
该顺序对顾客有利（退款时本金留得更多），且首期赠款恒 0，行为上等价于全扣本金。

### 6. 余额支付进 `payments`，但柜台方式枚举不含 `balance`

新增 `member.balance.pay` 命令。它在**同一事务**里做两件事：

1. 向 `member_ledger` 追加一条负增量（消费）；
2. 向 `payments` 追加一条 `method = 'balance'` 的支付行。

理由：余额结账在账面上就是一笔针对订单的支付，必须进 `payments`，否则订单的
`paid_cents` / `balance_cents` 与日结对账都会漏掉它。另立一张"储值支付表"会让
「订单收了多少钱」出现两个真源。

**但柜台可选的支付方式不得包含 `balance`。** 两个集合必须分开：

| 集合                     | 取值                           | 用途                         |
| ------------------------ | ------------------------------ | ---------------------------- |
| `PAYMENT_METHODS`        | cash / wechat / alipay / other | `payment.collect` 等命令入参 |
| `PAYMENT_LEDGER_METHODS` | 上列 + **balance**             | `payments` 表可容纳的取值    |

若 `payment.collect` 接受 `method='balance'`，店员就能给订单记一笔余额支付而**没有
任何一条会员账本借记**——钱凭空出现，且账本与订单两侧都各自"自洽"，事后极难发现。
命令层的枚举因此保持不变（`PaymentMethodSchema` 未动，冻结的输入 schema 不受影响），
只有数据库 CHECK 与账本层容纳 `balance`，且唯一的写入路径是 `member.balance.pay`
的同事务双写。

`packages/domain` 中原本还有一份硬编码的方法名副本（`payment-ledger.ts`），本次改为
从 `PAYMENT_LEDGER_METHODS` 派生：两份清单意味着新增方法时漏改一处就静默拒绝。

### 7. 并发：账户行加锁后复核，余额不得为负

余额扣减路径必须 `SELECT ... FROM member_accounts ... FOR UPDATE` 锁住账户行，**在锁内**
重新求和、校验余额充足，再插入账本行。账户行是这条资金线的锁锚点。

不允许透支：锁内余额不足直接拒绝。ADR-03 的整数分与"业务变更与审计同事务"继续适用。

### 8. 风险等级与离线档位

| 命令                  | 风险   | 离线   | 理由                                  |
| --------------------- | ------ | ------ | ------------------------------------- |
| `member.account.open` | R2     | denied | 建档类操作，与 `customer.upsert` 同档 |
| `member.topup`        | **R3** | denied | 真金白银入账，不可逆，须二次确认      |
| `member.balance.pay`  | R2     | denied | 随订单支付档位，但离线禁止（见下）    |

三条全部 `offline_mode: denied`。离线期无法对组织级余额取得权威读，两台设备同时离线
消费同一余额必然透支，而透支后没有任何补偿手段——钱已经花了。储值线**不进离线队列**，
直到 offline grant 链路具备权威余额租约。

### 9. 顾客合并时，双方都有账户则拒绝

`customer.merge` 若发现被合并的两个顾客**都**持有会员账户，直接拒绝并返回明确错误，
要求先人工处理余额。单侧持有账户时，账户随存活的 `customer_id` 迁移。

理由：自动合并余额看似便利，但两个账户可能有不同的本金/赠款构成与退款权利，合并规则
属于资金裁决而非工程默认值。拒绝比悄悄合错更安全。

## 交付切片

本 ADR 的范围分两片落地，**第一片不改变用户可见能力**：

1. **地基（本 PR）**：迁移 0032、契约面（3 命令 + 1 查询）、`PAYMENT_METHODS` 与
   `PAYMENT_LEDGER_METHODS` 拆分、纯余额投影与扣减分配及其单测。命令此时**仅有定义、
   尚未注册 handler**——与 `identity.logout` 同形态，调用会得到未注册错误。因此本片
   **不进 CHANGELOG**：柜台看不到任何变化，按 CHANGELOG 自身的口径它不是面向用户的变化。
2. **接线（下一片）**：`member_accounts` / `member_ledger` 的内存与 PostgreSQL 存储、
   三个命令与一个查询的 handler、`register-m1` 注册、真实 PG 回归，以及柜台 UI。
   该片合入时才更新 CHANGELOG。

分片的理由是资金路径的锁与并发必须单独验证，把它和 schema、契约混在一个 PR 里评审，
真正需要盯的那 30 行会被 300 行样板淹没。

## 首期不做

- **充值赠送与分档规则**（满额赠、阶梯赠）：涉及本金/赠款比例与退款权利，属资金合规裁决
- **积分**：与储值是两套激励，不共用账本
- **微信支付对接**：需商户资质与外网回调，属 ADR-14 阶段三；首期充值走现有线下收款方式
- **提现与储值退款**：R4/R5 级资金出账，须单独 ADR 与审批链
- **余额有效期与失效**：涉及预付卡法规，须单独裁决
- **跨组织通用**：组织仍是租户边界，不跨越

## 后果

- v0.2 命令面由 29 条增至 **32 条**（`member.account.open`、`member.topup`、
  `member.balance.pay`），查询增 1 条（`member.account.get`）。按 ADR-16 §2，本 ADR
  即为该次增长的裁决记录，`m2-freeze.test.ts` 清单变更在 PR 描述中点名。
- 新增迁移 `0032`：`member_accounts`、`member_ledger`，并扩 `payments_method_chk`。
- `payments.method` 新增 `'balance'`：读取支付方式的既有代码需能处理该值；统计与对账把
  余额支付计入订单收款，但它**不是当日现金流入**——充值时才是。
- 顾客脱敏（`customer.anonymize`）不清除账本：资金流水的留存义务优先于脱敏，脱敏只作用于
  身份字段。

## 否决的备选

- **在 `customers` 上加一个 `balance_cents` 列**：可 UPDATE 的余额无法自证，且与
  append-only 账本的既有姿态冲突，否决。
- **账户做成门店级**：与组织级的 `customers` 不一致，且 A 店充值 B 店不可用，不符合
  顾客预期，否决。
- **余额支付另立支付表**：会让「订单收了多少钱」出现两个真源，破坏对账，否决。
- **首期就做充值赠送**：赠款的退款权利未裁决，做了就要背着一个错误的资金模型上线，否决。
- **储值允许离线消费**：离线期无权威余额，必然透支且无补偿手段，否决。
- **顾客合并时自动合并余额**：合并规则属资金裁决，静默合错比拒绝危险，否决。
