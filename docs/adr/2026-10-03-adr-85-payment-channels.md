# ADR-85：Windows 微信支付与支付宝通道

- 日期：2026-10-03
- 状态：实现验收中；真实商户凭据、签约与实付验收待门店配置
- 范围：活动 V2 Windows；不恢复 Cloud 开发部署，不发送测试费用

## 裁决

微信采用直连商户 API v3、公钥模式（明确配置平台公钥 ID），支持柜台 Native 与顾客小程序 JSAPI；支付宝采用官方 v3 RSA2 协议与当面付二维码。服务端只访问两个固定 HTTPS 官方域名，不接受调用方提供的网关、重定向或代理地址。回包验签、时间窗、商户身份、订单号和整型分金额检查通过后才接受结果。微信通知另需 AES-256-GCM 认证解密；支付宝通知拒绝重复字段，表单只解码一次。

系统新增四个租户表：`payment_channel_settings`、`payment_channel_intents`、`payment_channel_refunds`、`payment_channel_reconciliations`（0075）。收款和退款先在事务中持久化唯一商户流水与派发标记，再调用网络。响应超时或无法验证时显示“结果待核实”，重试只查原流水，不生成第二笔资金请求。后台有界轮询和签名通知共用锁定、幂等结算函数。Windows 只有本机地址时，主动查询仍可完成记账；接收外部通知需要另行配置真实可达 HTTPS 地址，当前没有部署该入口。

现有 `payments` 与 `member_ledger` 继续作为财务权威账本。成功结果、账本引用和审计在同一事务中提交。闭账、余额或约束阻断时保留已核实通道结果和明确待处理状态，事务保存点保证不存在半条账。界面或原生微信支付的成功回调不作为收款证据。

## 退款与并发

新增命令 **`payment.channel.refund` v1.0.0**，风险 R4，仅在线，经既有确认、提权与审批链。参数仅有意向 ID、整数分金额及有限原因枚举。订单退款要求 `payment_refund`；会员充值退款还要求 `member_refund`。不可退赠送额，退款额同时受原交易剩余可退额与账户未消费本金约束。

在途收款阻止同订单重新收款、改价、取消和手工入账。充值同账户存在未决交易时不再创建第二笔。退款在途预留本金；原有 `payment.refund` / `member.refund` 不能对已绑定渠道的钱直接作手工退款。两个只读触发器以固定 owner/search_path 读取同组织的跨门店预留并锁账户，不给应用角色增加表读取权限或任意写入函数。缺少租户上下文的应用写入失败，可信迁移 owner 仍可恢复历史账本。

`m2-freeze.test.ts` 的命令清单同批增加上述命令（82 → 83），查询清单不变。柜台通道操作由固定 HTTP/IPC 合同接入；管理员会话派生全部租户参数，敏感配置另校验当前管理员密码与会话版本。顾客交易只能通过 ADR-86 的固定委托执行入口调用内部持久化服务。

## 密钥与恢复

商户私钥、平台公钥和微信 API v3 密钥通过现有 Windows DPAPI/KMS 信封存储，字段不进入日志、审计或整店业务导出。配置返回安全商户标识、版本与状态，不返回密钥。已有历史流水后不能切换商户身份；同身份允许轮换密钥。停用只阻止新派发，历史交易仍可查证。

跨机恢复排除支付配置并要求重新录入；所有未终结意向/退款改为待核实，保留原商户流水、金额和派发标记。不能据恢复后的记录盲目重发。A9 精确 schema、读者列授权、租户矩阵和迁移库存随新表同步；导出不包含 checkout 支付调用参数、会话或幂等执行凭据。

## 对账与界面

管理员从商户平台取得账单，将规范行导入通道对账界面。系统逐行核对原商户流水、通道交易号、金额和记账状态，并报告缺失、重复、状态或金额差异；完整输入摘要与结果同事务审计。该输入不触发扣款、退款或账本补写。金额在输入输出与比较中始终使用整数分；超大或重复账单有显式拒绝/差异记录。当前未实现商户账单自动下载任务。

柜台设置页提供密钥配置、收款二维码、状态查询、关闭未付单、原路退款与账单差异查看。顾客小程序用同一意向服务恢复未决付款（ADR-87），不自动重发未知交易。

## 验证与边界

协议测试使用临时 RSA 密钥、合成签名回包、合成加密通知和注入传输，覆盖篡改/过期/重复字段/错误商户/金额及网络边界，禁止真实 API 消费。真实 PostgreSQL 测试覆盖78迁移、锁定幂等、跨店预留、审计回滚、管理员密码、签名后单次记账及原路退款。最终通过数以同批执行日志为准。

正式 Windows 原生构建、安装操作与真实商户签约/实付属于不同验收证据。没有真实商户凭据的协议测试不代表商户已开通，未以合成数据替代生产准入。
