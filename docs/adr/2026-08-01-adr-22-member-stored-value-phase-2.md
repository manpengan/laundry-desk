## 背景

ADR-17 / ADR-18 交付了储值首期：开户、充值、余额结账、只追加账本、核销单列对账。
二期要解决两件事——**充值赠送**（充值转化的直接杠杆）与**退款权利**（赠送一旦开始，
「我充 1000 送 100，退卡退多少」立刻成为柜台每天要回答的问题）。

ADR-17 §首期不做 已经写明赠送被推迟的原因：

> **充值赠送与分档**（满额赠、阶梯赠）：涉及本金/赠款比例与退款权利，属资金合规裁决

本 ADR 处理该裁决。但在起草过程中，先查出一个**已上线的资金缺陷**，它必须先修，
否则赠送会把误差放大——见 §1。

## §1 缺陷：现金充值不进当日现金，交班必然长款

### 现象

`member.topup` 的入参含 `method`（cash / wechat / alipay / other），但：

1. `member_ledger` **没有存放收款方式的列**（迁移 0032 的列表里没有）；
2. handler 只把 `method` 写进审计 JSON 的 `afterJson`
   （`apps/server/src/member/handlers.ts:160`），不落业务表；
3. `expected_cash_cents` 只统计 `payments` 表中 `method = 'cash'` 的行
   （`apps/server/src/stats/pg-source.ts:97`），而充值**不写 `payments`**
   （ADR-17 §6 只让 `member.balance.pay` 双写）；
4. `stats/`、`shift/`、`reconciliation/` 三个模块对 `member_ledger` **零引用**。

因此：顾客现金充值 1000 元 → 抽屉实收 1000 → 当日期望现金不含这 1000 →
**交班现金长款 1000，且账面上没有任何地方能解释它从哪来**。

### 这与 ADR-18 的裁决直接冲突

ADR-18 §3 写明：

> **现金流入**：不包含[余额支付]。钱在**充值当天**就已进店，计入充值那天的现金。

前半句成立（ADR-18 §1 已固化并补了回归），**后半句没有实现**。ADR-18 只补了
「余额支付不进钱箱」这一侧的回归，没补配对的「充值现金进钱箱」，所以门禁全绿。

按 ADR-16 §4，判定口径以 `main` 代码为准——这里是**代码没跟上已生效的裁决**，
属缺陷，不属待办。

### 决策

**1.1** `member_ledger` 新增 `tender text` 列，记录该笔资金**实际的现金渠道**：
充值记收款方式，退款（§4）记出款方式，`kind = 'pay'`（余额核销）恒为 `NULL`
——核销不产生现金进出，ADR-18 §1 已裁定。

两条约束：

- `member_ledger_pay_tender_chk`：`CHECK (kind <> 'pay' OR tender IS NULL)`
  ——核销不许带渠道；
- `member_ledger_tender_value_chk`：`CHECK (tender IS NULL OR tender IN
('cash','wechat','alipay','other'))` ——带了渠道就必须是现金汇总读得懂的那几种。

第二条**不要求非核销行必须带渠道**：0035 之前的历史充值行没有这一列，其渠道已无从
追认，强制非空会让迁移失败。这些行留 `NULL`，因而不进现金口径——与它们此前的行为
一致，不会凭空改写已交班的日子。

由数据库机械保证而不是靠 handler 自觉：`member_ledger` 对应用角色只授 `SELECT,
INSERT`，任何未来的写入路径都绕不开这两条 CHECK。

**1.2** 当日现金净额的定义扩为：

```
现金净额 = payments 中 method='cash' 的净额
         + member_ledger 中 tender='cash' 的 principal_delta_cents 之和
```

充值为正（钱进抽屉），退款为负（钱出抽屉）。

**只取 `principal_delta_cents`，不取 `bonus_delta_cents`**——赠款是账面赠与，
顾客没有为它付钱，抽屉里也没有对应的纸币。若把赠款计入现金，充 1000 送 100 会让
期望现金变成 1100，交班必然短款 100，正好制造出本节要消灭的那类无法解释的差额。

**1.3** 新增回归，与 ADR-18 既有的「余额支付不进钱箱」并列钉死：

- 现金充值 → 期望现金增加**充值本金**，不含赠款
- 微信/支付宝/其他充值 → 期望现金**不变**
- 余额核销 → 期望现金不变（ADR-18 已有）
- 现金退款（§4 交付后）→ 期望现金减少

### 交付

**§1 已交付**（迁移 `0035_member_tender_cash_reconciliation.sql`）：`tender` 列与两条
CHECK、部分索引 `member_ledger_cash_day_idx`、memory 与 PostgreSQL 两侧的
`sumCashPrincipal`、两条统计源的现金汇总，以及 §1.3 的回归。

它不依赖 §2–§5 的任何产品裁决，因此先行合入，没有等赠送口径。

## §2 赠送规则的形态

### 裁决

**赠送用满额档位（阶梯），不用比例。** 档位对顾客是「充 1000 送 100」这种可直接印在
台卡上的话术，比例需要顾客自己算；且档位天然是整数分，比例会引入取整规则（向上还是
向下、是否按分四舍五入），每一条都是将来对账争议的来源。

**规则是组织级，不按门店。** 余额本身就是组织级通用（ADR-17 §2），A 店充值 B 店可用。
若规则按门店走，顾客会发现同样充 1000 在两家店送得不一样，而钱又是通用的——这个组合
没法向顾客解释。

### 决策

**2.1** 新表 `member_bonus_rules`（组织级 RLS，照抄 `member_accounts` 的
`customers_org_scope` 姿态）：

| 列                | 说明                 |
| ----------------- | -------------------- |
| `min_topup_cents` | 命中门槛，整数分     |
| `bonus_cents`     | 赠送额，整数分       |
| `status`          | `active` / `retired` |
| `effective_from`  | 生效时间             |

命中规则：取 `status='active'` 且 `min_topup_cents <= amount_cents` 中
`min_topup_cents` **最大**的一条；无命中则赠送为 0。

**2.2 停用不删除**，照抄价目维护（ADR-15）的姿态：`retired` 只下架，历史账本引用的
规则行必须保留可读。

**2.3** 新增命令 `member.bonus_rule.upsert`（R3）与查询 `member.bonus_rules.list`（R1）。

改赠送规则需要**单独的权限位 `member_rule_write`**，不复用 `catalog_write`：改赠送直接
改的是资金赠与额度，与改一项服务的售价不是同一类风险，把两者绑在一个权限位上意味着
任何能调价的人都能调赠送。

命令面由 **32 → 33**，查询 +1。按 ADR-16 §2，本 ADR 即该次增长的裁决记录，
`m2-freeze.test.ts` 清单变更须在 PR 描述点名。

## §3 赠送金额由服务端计算，命令入参一个字不动

### 决策

**3.1** `MemberTopupInputSchema` **保持不变**——不新增 `bonus_cents` 入参。

理由与 ADR-17 §6 拒绝 `method='balance'` 同源：若客户端能提交赠送额，店员就能给任意
充值配任意赠送，而账本两侧都各自"自洽"，事后极难发现。赠送额必须由服务端按
`member_bonus_rules` 算出，与权威计价「金额以服务端为准」同一条原则。

**3.2** `member.topup` 是 **R3**，本来就有二次确认。服务端在第一跳的确认摘要里返回
算出的赠送额与命中的规则，店员在第二跳前看得到「充 1000，送 100，到账 1100」。
**不需要新增预览命令**。

**3.3** 命中的规则 id 与当时的赠送额**快照进 `member_ledger`**（新增
`bonus_rule_id uuid` 列，`kind='topup'` 且赠送 > 0 时非空）。后续改规则或停用规则
**不影响历史行**——与订单的价格快照同一姿态。

**3.4** 赠送落在充值行的 `bonus_delta_cents` 上，与 `principal_delta_cents` 同一行。
不另起一条「赠送行」：同一次充值拆成两行会让 `ledger_seq` 相邻两行必须成对读取，
任何漏读一行的查询都算错余额。首期定的
`member_ledger_topup_sign_chk`（两个 delta 均 ≥ 0 且和 > 0）已经容纳这个形态，
**无需改动该约束**。

## §4 退款权利：可退 = 剩余本金，赠款不退不折现

**这是本 ADR 的核心，也是唯一改错了就无法挽回的一条**——账本只授
`SELECT, INSERT`，口径定错只能靠冲正，改不动历史。

### 决策

**4.1 赠款不可退现，不可折现，不可转让。**

**4.2 可退金额 = 当前余额投影的 `principal_cents`**，不做任何回溯计算。

这条之所以成立，是 ADR-17 §5「先扣赠款、后扣本金」的直接结果：因为消费永远优先
吃掉赠款，剩下的 `principal_cents` **恰好就是尚未被消费的本金**。可退金额是一个
已经存在的投影值，不需要遍历历史、不需要拆分流水、不需要任何新算术。

举例（充 1000 送 100，消费 100 后退卡）：

| 顺序                 | principal | bonus | 可退     |
| -------------------- | --------- | ----- | -------- |
| 充值后               | 1000      | 100   | —        |
| 消费 100（先扣赠款） | 1000      | 0     | **1000** |
| 若改为先扣本金       | 900       | 100   | 900      |

先扣赠款对顾客有利，这一点 ADR-17 §5 已经写明，本节只是把它的**退款侧后果**固化。

**4.3 不追扣已享受的赠送优惠。**

上例中顾客消费了 100 却拿回全部 1000 本金，等于白用了 100 赠款。这是有意接受的成本。

理由三条：

1. **法规侧**：单用途预付卡的通行要求是未消费金额可退；在开户条款没有明示的情况下
   事后追扣赠送优惠，容易被认定为不合理条款；
2. **账本侧**：追扣需要回溯「这笔消费当时吃掉了多少赠款」，而账本只追加、拆不动。
   要支持追扣就得改账本形态——正是 ADR-17 §5 分列本金/赠款所要避免的那种回溯；
3. **风险侧**：单店规模下，把赠送比例调低一档就能覆盖这个损失，比事后追扣简单得多，
   也不会在柜台制造「为什么退我这么少」的争执。

**4.4** 该成本**已被接受**。「按已消费比例追扣赠送优惠」的备选被否决：它需要每条消费行
记录当时吃掉的赠款来自哪条充值，会推翻 §3.4 的单行形态；且未在开户条款明示时追扣，
本身就是争议来源。若将来要改为追扣，必须先改会员条款并留痕顾客确认，且要另起一套账本
设计——那是一份新的 ADR，不能靠修订本文完成。

## §5 退款执行：新增 `member.refund`，R4 + step-up

### 决策

**5.1** 新增命令 `member.refund`，姿态照抄既有的 `payment.refund`
（`packages/contracts/src/commands/payment.ts:67`，R4、`offline_mode: "denied"`、
引用原行、只追加、绝不改原行）：

| 属性           | 取值                                                                         |
| -------------- | ---------------------------------------------------------------------------- |
| `risk`         | `R4`（资金出账，须 step-up 身份复核）                                        |
| `offline_mode` | `denied`（离线无权威余额，与其余三条储值命令一致）                           |
| 入参           | `account_id`、`amount_cents`、`tender`、`reason`（必填非空）                 |
| 不变式         | `rbac.member_refund`、`member.account_active`、`member.refundable_principal` |

`reason` 必填且非空，与 `order.cancel` 同姿态：资金出账必须留下人写的理由。

**5.2** `member_ledger.kind` 的 CHECK 由 `IN ('topup','pay','reversal')` 扩为
`IN ('topup','pay','reversal','refund')`，并加两条约束：

- `CHECK (kind <> 'refund' OR (principal_delta_cents < 0 AND bonus_delta_cents = 0))`
  ——**赠款不退由数据库机械保证**，不靠 handler 自觉。§4.1 的裁决因此不可能被一次
  错误实现绕过；
- `CHECK (kind <> 'refund' OR order_id IS NULL)` ——退款不挂订单。

**5.3** 退款走与消费相同的并发姿态（ADR-17 §7）：`SELECT ... FOR UPDATE` 锁账户行，
**锁内**重新求和，校验 `amount_cents <= principal_cents`，再插入账本行。
不允许退成负数。

**5.4** 现金退款进当日现金净额（负），按 §1.2 / §1.3 的口径。

**5.5** 退款**不写 `payments`**。`payments` 是订单收款的真源，储值退卡与任何订单都
无关，写进去会让「这一单收了多少钱」出现一笔不属于任何订单的行。

**5.6 退款执行进二期。** 赠送一旦上线，退卡争议的发生概率显著上升；若只裁口径而不给
执行入口，店员面对要求退卡的顾客只有两个选择——手工从抽屉拿钱而账上不记（制造无法
解释的短款，正是 §1 要消灭的那类差额），或者用 `reversal` 冲正（污染冲正的语义，
冲正是用来改错账的，不是退款）。两个都比交付 `member.refund` 差。

## 二期仍不做

沿用 ADR-17 §首期不做，以下继续后置：

- **积分**：与储值是两套激励，不共用账本
- **微信支付对接**：需商户资质与外网回调，属 ADR-14 阶段三，且它改的是收款渠道
  而非储值模型，应当**单独 ADR**，不并入本文
- **余额有效期与失效**：涉预付卡法规，须单独裁决
- **储值卡转赠 / 跨组织通用**：组织仍是租户边界

- ADR-18 §3 后半句由 §1 落地；ADR-18 本身无需修订，它的裁决是对的，缺的是实现。

## 否决的备选

- **赠送额由客户端提交**：店员可给任意充值配任意赠送且事后难查，与 ADR-17 §6
  拒绝 `method='balance'` 同源，否决。
- **赠送单独起一条账本行**：同一次充值拆两行，漏读一行即算错余额，否决。
- **赠款可退现**：赠款是账面赠与，退现等于把营销成本变成可套现的现金，
  且会诱发「充值—立即退卡」套利，否决。
- **可退金额按总充值本金减总消费计算**：与「先扣赠款」的既有顺序不一致，会算出比
  §4.2 更低的可退额，等于事实上追扣赠送而没有明示，否决。
- **退款写入 `payments`**：会在订单收款真源里放入不属于任何订单的行，否决。
- **退款用 `reversal` 代替**：冲正是改错账，退款是资金出账，混用会让两者都失去
  可审计性，否决。
- **把 §1 的修复并入赠送切片**：让一个已在生产上制造现金长款的缺陷等待产品裁决，
  否决。
