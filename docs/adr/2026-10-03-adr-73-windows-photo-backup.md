# ADR-73：Windows 本机照片与数据库联合备份恢复

- 日期：2026-10-03
- 状态：实现；Windows 安装态验收待执行
- 前置：[ADR-68](2026-09-30-adr-68-windows-managed-backup-restore.md)、[ADR-71](2026-10-02-adr-71-cloud-platform-pause.md)

## 背景

Windows runtime 原先未设置照片目录，配置解析只接受容器挂载路径；照片根初始化还依赖 POSIX 目录文件描述符。ADR-68 因此在发现照片目录或照片行时拒绝数据库备份。用户已授权 Windows 全功能开发及分批提交，打印工作延后、Cloud 部署继续暂停。

## 裁决

1. Windows runtime 默认启用当前用户 `%LOCALAPPDATA%\laundry-desk-v2\runtime-companion\photos`。Windows 配置仅接受这个确定目录，拒绝 UNC、设备路径、路径穿越、ADS 和任意磁盘位置；非 Windows 保留原容器路径限制。
   新服务器识别已安装 Windows runtime 的既有发行标记；旧登录控制器缺少照片环境变量时，同样推导并验证这个固定目录，使升级后重新登录仍启用照片。无效/缺少当前用户根失败关闭。
2. 复用既有照片 HTTP/IPC、SPA 与事务审计，不新增业务 Command/Query。照片仍以服务器 UUID 命名，限制单张 8 MiB、总计 2 GiB、10,000 个文件；校验真实类型、SHA-256 和私有存储权限。Windows 的目录、文件保护与持久化通过现有 Win32 helper 执行 DACL、唯一文件链接和重解析点检查，不以 POSIX mode 模拟 ACL。
   Windows 文件发布使用同目录 `MoveFileExW` 的 `WRITE_THROUGH` 且不设 `REPLACE_EXISTING`，避免原 `link→unlink` 在断电后留下两个硬链接；目标存在时原子拒绝覆盖，并复核文件标识。POSIX 保留既有发布策略。
3. 新托管备份采用 `laundry.windows.backup` version 2：`database.dump`、`photos.json`、`photos/` 与最后发布的 `backup.json`。照片索引包含受限文件名、字节数和 SHA-256，独立限制为 2 MiB；不会扩大维护状态文件的 64 KiB 限制。
4. 备份先停止业务写入，再校验迁移账本、照片行与真实文件，生成数据库 dump 及照片快照。照片行缺文件、散列不符、旧元数据缺散列、不属于本产品的目录内容、链接或超限均拒绝发布。上传暂存文件不作为业务照片归档；有效孤立照片可保留在快照中。
5. 恢复先验证完整归档并建立当前数据库/照片安全备份，恢复到影子数据库；验证影子数据库引用的照片全部存在于目标归档，然后将缺少的不可变照片补入本机照片库，最后执行既有数据库 OID 绑定切换。UUID 碰撞不会覆盖当前文件。
6. 文件系统与 PostgreSQL 没有跨资源事务：通过“先补齐不可变文件，再切换引用”保证任意可启动数据库只指向已验证照片。旧照片保留以便切换前的故障回退；维护日志非 idle 时禁止业务启动。显式恢复按原有 verified 提交点决定保留新数据库或恢复旧数据库；不清除未知归档、不静默删除恢复点。
7. version 1 数据库备份继续可读取，视为没有照片，影子数据库出现照片行时拒绝恢复。版本、同实例、确认摘要、PostgreSQL 主版本及迁移一致性限制继续生效；离机导出、换机恢复、定时保留和跨迁移恢复属于后续 A2–A4。

## 验证要求

- 本机回归：照片归档与重复恢复、UUID 碰撞、缺失/篡改/额外文件、硬链接、无主目录、旧版归档兼容、DB 引用缺失、恢复/切换/清理中断一致性。
- Windows 门禁：安装包原生照片保存与读取、真实 NTFS DACL、照片与真实 PostgreSQL 行一起备份/删除/恢复、恢复安全点、安装态柜台照片上传预览流程。`backup-acceptance.mjs` 已增加原生联合备份场景；脚本存在不代表该场景已执行。
- 当前发行仍为 `development_only`，真实顾客数据与生产准入按另行 ADR 裁决。
